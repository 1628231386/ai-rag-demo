# Redis 核心考点速查

## 缓存穿透
缓存穿透是指查询一个数据库里根本不存在的数据。缓存查不到，就会去查数据库，数据库也查不到，所以这次查询不会写回缓存。如果有人恶意用大量不存在的 id 反复请求，每一次请求都会直接打到数据库上，数据库压力陡增甚至被打垮。

解决办法有两种。第一种是布隆过滤器，把一个集合里所有存在的 key 通过多个哈希函数映射到一个位数组上，查询前先过一遍过滤器，判断这个 key 一定不存在就直接返回，挡掉绝大部分无效请求。布隆过滤器的特点是不存在漏报，但存在很小的误判率，也就是说它可能把不存在的 key 判成存在，但不会把存在的判成不存在。第二种办法是把查不到的空值也缓存起来，也就是缓存空对象，给这个 key 存一个 null 值并设置一个较短的过期时间，比如五分钟，这样后续相同的请求就不会再打到数据库了。两种方案通常配合使用。

## 缓存击穿
缓存击穿是指某一个热点 key 在缓存过期的那一瞬间，恰好有大量的并发请求同时进来。这些请求发现缓存失效，就一起去查数据库重建缓存，导致数据库瞬间压力剧增。注意缓存击穿针对的是单个热点 key，而缓存雪崩针对的是大批 key 集体失效。

解决办法主要是互斥锁和逻辑过期。互斥锁的做法是，当发现缓存失效时，先去获取一把分布式锁，拿到锁的线程才去查数据库重建缓存，没拿到锁的线程睡眠一小会儿再重试。这种方案能保证数据一致性，但会有线程等待，性能稍差。逻辑过期的做法是，缓存里的数据不设置过期时间而是永不过期，但在 value 里额外存一个逻辑上的过期时间戳。当发现超过这个时间时，拿锁的线程开一个新线程去异步重建缓存，自己先把旧数据返回给用户。这种方案性能好，但在重建完成前用户会读到稍微陈旧的数据。这两种方案分别对应一致性和可用性的取舍。

## 缓存雪崩
缓存雪崩是指在同一时间大批量的 key 集中过期，或者 Redis 服务直接宕机不可用，导致原本由缓存承担的请求像雪崩一样全部压到数据库上，数据库扛不住而崩溃。

解决思路是让 key 的过期时间分散开。可以在设置过期时间时，在基础过期时间上再加一个随机值，比如基础三十分钟再加一到五分钟的随机数，避免同一秒创建的大量 key 在同一秒集体失效。此外还要依赖 Redis 的高可用方案，比如哨兵模式和集群模式保证服务不整体挂掉。在应用层还要做限流和降级，保证数据库不会被瞬间打死。提前做缓存预热，把热点数据在活动开始前就加载到缓存里，也是常用手段。

## Redis 持久化
RDB 是 Redis Database 的缩写，它在指定的时间间隔内把内存中的数据快照完整地写入磁盘，生成一个二进制的 dump.rdb 文件。它的优点是文件紧凑、恢复速度快，适合做冷备份。缺点是会丢失最后一次快照之后的所有数据，数据完整性较差。

AOF 是 Append Only File 的缩写，它把每一条写命令都追加记录到日志文件的末尾，Redis 重启时重新执行这些命令来恢复数据。它的数据完整性好，可以配置成每秒同步甚至每条命令同步，丢失数据极少。缺点是日志文件会不断膨胀，体积远大于 RDB，而且数据恢复速度比 RDB 慢。Redis 提供了 AOF 重写机制来压缩日志，把多条命令合并成一条最终状态的命令。生产环境通常两者同时开启，用 AOF 保证数据完整性，用 RDB 做备份和快速恢复。

## Redis 主从复制
主从复制的核心目的是读写分离和数据冗余。主节点负责处理写请求，从节点复制主节点的数据并承担读请求，从而分摊读压力，并在主节点故障时可以由从节点顶上。

全量同步发生在从节点第一次连接主节点的时候。从节点向主节点发送 sync 命令，主节点执行 bgsave 生成 RDB 快照文件并发送给从节点，从节点清空自己的旧数据后加载这个快照。在主节点生成快照期间新写入的命令会记录在一个缓冲区里，快照发完后再把这些增量命令补发给从节点，保证数据最终一致。

增量同步发生在网络闪断后的重连场景。主节点把断连期间产生的写命令记录在一个环形的复制积压缓冲区里，从节点重连时上报自己已经同步到的偏移量，主节点只需要把偏移量之后的这部分命令补发过去即可，不需要再做全量 RDB，代价小得多。

## Redis 数据类型使用场景
String 是最基础的类型，可以用来做分布式锁、计数器、存验证码，也可以序列化后存对象。Hash 适合存储对象类的结构化数据，比如购物车，可以把商品 id 作为 field，数量作为 value，这样修改某个商品不用把整个对象重新序列化。List 底层是双向链表，适合做消息队列和最新动态列表，比如朋友圈时间线。Set 是无序且不重复的集合，适合做共同好友、标签系统、抽奖去重。ZSet 是有序集合，每个成员关联一个分数，适合做排行榜、延迟队列、带权重的优先级任务。
